## 1. Introduction

When starting with **SQLMap**, the first thing to learn is its **help system**.

SQLMap provides two main levels of help:

|Command|Purpose|
|---|---|
|`sqlmap -h`|Basic help|
|`sqlmap -hh`|Advanced/full help|

### Easy way to remember

```text
-h
 ↓
Basic options

-hh
 ↓
Advanced options
```

---

# 2. Basic Help — `-h`

Run:

```bash
sqlmap -h
```

This displays the most commonly used SQLMap options.

Important options include:

```text
-h, --help
    Show basic help message and exit

-hh
    Show advanced help message and exit

--version
    Show program's version number and exit

-v VERBOSE
    Verbosity level: 0-6
```

---

## 2.1 Verbosity Levels

The `-v` option controls how much information SQLMap prints.

```bash
sqlmap -v 3 -u "http://target/page.php?id=1"
```

Conceptually:

```text
-v 0
 ↓
Very little output

-v 1
 ↓
Default

-v 2
 ↓
More information

...

-v 6
 ↓
Maximum verbosity
```

Higher verbosity is useful when troubleshooting or trying to understand exactly what SQLMap is doing.

---

# 3. Advanced Help — `-hh`

Run:

```bash
sqlmap -hh
```

Unlike `-h`, this displays the **advanced listing**, containing a much larger set of SQLMap options.

The advanced help is especially useful when working with:

- Custom HTTP requests
    
- Cookies
    
- Headers
    
- POST requests
    
- Burp Suite requests
    
- Multiple targets
    
- Specific DBMSes
    
- Injection techniques
    
- Enumeration
    
- Authentication
    
- Optimization
    
- WAF-related testing
    
- Advanced SQLMap behavior

# 4. SQLMap Target Options

The target section tells SQLMap **what it should test**.

Important target options from the material:

|Option|Purpose|
|---|---|
|`-u URL`|Target URL|
|`-d DIRECT`|Direct database connection|
|`-l LOGFILE`|Parse targets from Burp/WebScarab logs|
|`-m BULKFILE`|Scan multiple targets from a file|
|`-r REQUESTFILE`|Load an HTTP request from a file|
|`-g GOOGLEDORK`|Process Google dork results as target URLs|
|`-c CONFIGFILE`|Load options from an INI configuration file|

---

# 5. `-u` — Target URL

The most basic and important SQLMap target option is:

```bash
-u
```

Example:

```bash
sqlmap -u "http://www.site.com/vuln.php?id=1"
```

This tells SQLMap:

> Test the specified URL and its parameters for SQL injection.

The URL:

```text
http://www.site.com/vuln.php?id=1
```

contains a GET parameter:

```text
id=1
```

SQLMap can test whether `id` influences a vulnerable SQL query.

---

# 6. `-d` — Direct Database Connection

```text
-d DIRECT
```

This is used when SQLMap is given a **direct database connection string** rather than attacking a web application URL.

This is a more advanced usage scenario.

---

# 7. `-l` — Parse Proxy Logs

```text
-l LOGFILE
```

SQLMap can parse targets from proxy log files, such as logs generated by tools like:

- Burp Suite
    
- WebScarab
    

Conceptually:

```text
Browser
   ↓
Burp Suite
   ↓
Captured HTTP Request
   ↓
SQLMap
```

This is useful when the target request is complicated and cannot conveniently be represented by a simple URL.

---

# 8. `-m` — Multiple Targets

```text
-m BULKFILE
```

This allows SQLMap to process multiple targets specified inside a text file.

Conceptually:

```text
targets.txt

http://lab1/page.php?id=1
http://lab2/page.php?id=2
http://lab3/page.php?id=3
```

SQLMap can process the targets from the file.

---

# 9. `-r` — Load an HTTP Request

```text
-r REQUESTFILE
```

This option loads an HTTP request from a file.

This is extremely useful for complex requests containing things such as:

- POST parameters
    
- Cookies
    
- Headers
    
- Authentication-related data
    
- Multiple parameters
    

Conceptually:

```text
Raw HTTP Request
       ↓
   request.txt
       ↓
     SQLMap
```

---

# 10. `-g` — Google Dork Results

```text
-g GOOGLEDORK
```

This option allows SQLMap to process search-engine results as target URLs.

This is an advanced feature and should only be used within an authorized scope.

---

# 11. `-c` — Configuration File

```text
-c CONFIGFILE
```

SQLMap can load options from a configuration INI file.

This is useful when repeatedly running SQLMap with the same configuration.

Instead of repeatedly typing many options:

```text
Option A

Option C
Option D
```

you can store them in a configuration file.

# 16. `--data` — POST Data

The `--data` option allows SQLMap to send data through POST.

Conceptually:

```http
POST /login.php HTTP/1.1

```

This is important because SQL injection is not limited to GET parameters.

# 17. `--cookie` — Cookies

SQLMap can send a custom HTTP Cookie header:


This is useful when the application requires an authenticated session.

Conceptually:

```text
Browser
   │
   └── Session Cookie
          ↓
       Application
```

SQLMap can use the same session context when authorized testing requires it.

# 18. Basic SQLMap Scenario

Consider a vulnerable PHP application.

The application receives:

```text
id
```

from a GET request.

The vulnerable code is:

```php
$link = mysqli_connect($host, $username, $password, $database, 3306);

$sql = "SELECT * FROM users WHERE id = " . $_GET["id"] . " LIMIT 0, 1";

$result = mysqli_query($link, $sql);

if (!$result)
    die("<b>SQL error:</b> ". mysqli_error($link) . "<br>\n");
```

---

# 19. Why This PHP Code Is Vulnerable

The dangerous part is:

```php
$_GET["id"]
```

being directly concatenated into the SQL query:

```php
$sql = "SELECT * FROM users WHERE id = " . $_GET["id"] . " LIMIT 0, 1";
```

The application effectively does:

```text
User Input
    ↓
$_GET["id"]
    ↓
SQL Query Construction
    ↓
Database
```

There is no proper parameterized query separating:

```text
SQL code
```

from:

```text
User-controlled data
```

---

# 20. What the Intended Query Looks Like

If the user requests:

```text
?id=1
```

the application constructs something conceptually equivalent to:

```sql
SELECT * FROM users WHERE id = 1 LIMIT 0, 1
```

The intended flow is:

```text
GET parameter
     ↓
id = 1
     ↓
SQL query
     ↓
Database
```

---

# 21. Why Direct String Concatenation Is Dangerous

The application treats the input as part of the SQL statement.

Conceptually:

```text
Trusted SQL
     +
Untrusted Input
     ↓
One SQL Statement
```

This is the fundamental problem behind SQL injection.

The secure approach is to use **parameterized queries / prepared statements**, so user input remains data rather than becoming SQL syntax.

---

# 22. Error Reporting

The vulnerable PHP code contains:

```php
if (!$result)
    die("<b>SQL error:</b> ". mysqli_error($link) . "<br>\n");
```

This means that if the SQL query fails, the application displays a database error.

Conceptually:

```text
SQL Query
   ↓
Database
   │
   ├── Successful
   │      ↓
   │   Normal response
   │
   └── Error
          ↓
     mysqli_error()
          ↓
     Web response
```

This is particularly useful during SQL injection detection because database errors may reveal useful information about the backend.

---

# 23. Why Error Messages Help SQLi Detection

Suppose normal input produces:

```text
id=1
```

and a malformed input causes:

```text
SQL error: ...
```

The difference can indicate that the input is reaching the SQL query.

This does **not automatically prove SQL injection**, but it provides an important clue.

# 24. Running SQLMap Against the Example

```text
http://www.example.com/vuln.php?id=1
```

SQLMap command:

```bash
sqlmap -u "http://www.example.com/vuln.php?id=1" --batch
```

Two important options here are:

```text
-u
```

```text
--batch
```

---

# 25. `--batch`

The `--batch` switch tells SQLMap to automatically answer prompts using its default choices.

Without `--batch`, SQLMap may ask questions such as:

```text
Do you want to skip tests?
[Y/n]
```

With:

```bash
--batch
```

SQLMap automatically selects the default answer.

### Remember:

```text
--batch
    ↓
No interactive questions
    ↓
Use default choices
```

This is particularly convenient for automated lab workflows.

---

# 26. Understanding the SQLMap Output

The example output is extremely important because it demonstrates the **complete detection workflow**.

SQLMap begins with:

```text
[INFO] testing connection to the target URL
```

Meaning:

> SQLMap first checks whether the target can be reached.

---

# 27. Content Stability Test

Next:

```text
[INFO] testing if the target URL content is stable
[INFO] target URL content is stable
```

SQLMap checks whether repeated requests produce reasonably consistent responses.

This is especially important for blind SQL injection.

Conceptually:

```text
Request 1 → Response A
Request 2 → Response A
Request 3 → Response A

       ↓

Stable baseline
```

If responses constantly change for unrelated reasons, SQLMap's inference can become difficult.

---

# 28. Dynamic Parameter Detection

SQLMap then tests:

```text
[INFO] testing if GET parameter 'id' is dynamic
[INFO] GET parameter 'id' appears to be dynamic
```

This means changing the `id` parameter affects the application's response.

Remember:

```text
Dynamic ≠ Vulnerable
```

It only means the parameter appears to influence the response.

---

# 29. Heuristic SQLi Test

SQLMap reports:

```text
[INFO] heuristic (basic) test shows that GET parameter 'id'
might be injectable
```

This is an early indication.

SQLMap has not yet completed its full testing.

Conceptually:

```text
Initial testing
      ↓
Potential SQLi
      ↓
Detailed technique testing
```

---

# 30. Heuristic XSS Test

The example also shows:

```text
[INFO] heuristic (XSS) test shows that GET parameter 'id'
might be vulnerable to cross-site scripting (XSS) attacks
```

This is important because SQLMap can perform some heuristic checks for other injection-related behavior.

However, the main purpose of SQLMap is SQL injection testing.

---

# 31. DBMS Identification

SQLMap then says:

```text
it looks like the back-end DBMS is 'MySQL'.
```

This is a major step.

Knowing the DBMS allows SQLMap to choose DBMS-specific techniques and payloads.

Conceptually:

```text
Unknown DBMS
     ↓
Fingerprinting
     ↓
MySQL
     ↓
MySQL-specific testing
```

---

# 32. Why DBMS Identification Matters

SQL syntax differs between systems.

For example:

```text
MySQL
PostgreSQL
Microsoft SQL Server
Oracle
SQLite
```

all have different features and syntax.

Therefore SQLMap can adapt its testing to the detected DBMS.

---

# 33. Boolean-Based Blind Detection

The example reports:

```text
[INFO] testing 'AND boolean-based blind - WHERE or HAVING clause'
```

Later:

```text
GET parameter 'id' appears to be
'AND boolean-based blind - WHERE or HAVING clause' injectable
```

This means SQLMap found a reliable response difference that can be used to infer TRUE/FALSE conditions.

---

# 34. Reflective Values

The output contains:

```text
[WARNING] reflective value(s) found and filtering out
```

A **reflective value** is input that appears in the application's response simply because the application echoes it.

This can interfere with SQLMap's response comparison.

Conceptually:

```text
Injected value
      ↓
Application echoes input
      ↓
Response changes
      ↓
Could look like SQL-related difference
```

SQLMap filters reflective content so that it can focus on meaningful response differences.

---

# 35. Error-Based Detection

The example then tests MySQL-specific error-based techniques:

```text
[INFO] testing 'MySQL >= 5.5 AND error-based...'
```

and later identifies:

```text
[INFO] GET parameter 'id' is
'MySQL >= 5.0 AND error-based ...' injectable
```

This demonstrates why DBMS fingerprinting matters.

SQLMap can select **MySQL-specific error payloads** rather than relying only on generic SQL.

---

# 36. Inline Queries

The output also shows:

```text
[INFO] testing 'Generic inline queries'
```

and:

```text
[INFO] testing 'MySQL inline queries'
```

SQLMap is checking whether inline query injection is possible.

---

# 37. Stacked Queries

The output includes:

```text
[INFO] testing 'MySQL >= 5.0.12 stacked queries (comment)'
```

SQLMap is testing whether multiple SQL statements can be executed in the relevant context.

Again:

```text
SQLi exists
     ≠
Stacked queries necessarily work
```

Each technique has to be tested separately.

# 38. Time-Based Blind Testing

The output shows:

```text
[INFO] testing 'MySQL >= 5.0.12 AND time-based blind (query SLEEP)'
```

Then:

```text

'MySQL >= 5.0.12 AND time-based blind (query SLEEP)' injectable
```

This demonstrates SQLMap using a MySQL-specific time-delay mechanism.

# 39. Why SQLMap Mentions a Statistical Model

The output contains:

```text
[WARNING] time-based comparison requires larger statistical model,
please wait........... (done)
```

Timing-based injection requires SQLMap to distinguish:

```text
Normal response time
```

from:

```text
Intentionally delayed response
```

Network timing can vary naturally, so SQLMap needs statistical analysis.

Conceptually:

```text
Normal requests
  ↓
0.2 sec
0.3 sec
0.4 sec
0.2 sec

Delayed request
  ↓
5.3 sec

       ↓

Likely intentional delay
```

# 40. UNION Query Testing

# 54. Important Difference: URL vs Request File

### Simple target

Use:

```bash
sqlmap -u "http://target/page.php?id=1"
```

Good when the request is simple.

### Complex target

Use:

```bash
sqlmap -r request.txt
```

Good when you need to preserve the complete HTTP request.

For example:

```text
POST /search HTTP/1.1
Host: target
Cookie: SESSION=...
Content-Type: application/x-www-form-urlencoded

id=1&search=test
```

A request file preserves this context.

# 55. Why SQLMap Tests Multiple Techniques

A target may support more than one SQLi technique.

The example demonstrates this clearly:

```text
One vulnerable parameter
        │
        ├── Boolean blind
        ├── Error-based
        ├── Time-based blind
        └── UNION-based
```

This is useful because different techniques have different advantages.

For example:

```text
UNION
 ↓
Often excellent for direct output

Error
 ↓
Useful when database errors are exposed

Boolean
 ↓
Useful when response differences exist

Time
 ↓
Useful when other channels are unavailable
```

---

# 56. Important Concept — One Vulnerability, Multiple Techniques

Do not assume:

```text
One SQLi
=
One technique
```

A single vulnerable parameter can support several SQL injection techniques.

The example proves this:

```text
id
│
├── Boolean-based blind
├── Error-based
├── Time-based blind
└── UNION-based
```

SQLMap automatically tests different possibilities.

`--batch` does **not** mean:


It means:

```text
"Do not ask me interactive questions;
use default answers."
```

This distinction is important.

# 60. Beginner Mistakes to Avoid

## Mistake 1 — Thinking dynamic means vulnerable

```text
Dynamic
≠
SQL Injection
```

---

## Mistake 2 — Ignoring DBMS identification

Payloads and SQL syntax can vary by DBMS.

---

## Mistake 3 — Assuming UNION always works

UNION-based SQLi depends on the query structure and output reflection.

---

## Mistake 4 — Assuming SQLi automatically means OS compromise

It doesn't.

Additional privileges and environmental conditions are required.

---

## Mistake 5 — Treating `--batch` as an exploitation mode

It simply automates interactive choices.

---

## Mistake 6 — Ignoring response stability

Blind SQLi depends heavily on reliable response comparison.
